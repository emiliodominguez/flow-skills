# Work

Deliver one verified slice at a time. Match the repository's conventions and prove the
requested behavior with evidence proportionate to the change.

## Phase 1: Select the task and execution profile

- **Execution Profile Override:**
  - If `--model` is supplied in the invocation or delegated task brief, configure or delegate execution to use that specified model engine for this task run.
  - If `--effort` is supplied, set the reasoning effort / thinking budget accordingly.
  - If the requested model is unavailable, log the fallback in the worker artifact and continue using the current active session model.

- An explicit plan path selects that plan. Read it and its referenced source; do not choose a
  different plan when the path is missing.
- A description selects direct work, even when old plans exist.
- A bare invocation may select the only unfinished ready/in-progress direct plan. Ask if
  multiple plans remain plausible. An orchestrated plan resumes through /ed-orchestrate.
- A coordinator's task brief selects delegated mode: execute only the assigned task and write
  set, then return an artifact. Do not edit shared plan state or claim gate acceptance.

Current user instructions take precedence over an older plan. Reconcile relevant source drift
before editing. A ready task needs observable acceptance and satisfied dependencies. Already
completed work need not be repeated; report or verify its current state.

## Phase 2: Ground the implementation

Read applicable instructions, nearby implementation/tests, configuration and pinned dependency
versions. Preserve required JSDoc, comments, formatting, logging and lint rules. A generic
preference such as fewer comments never overrides documented repository requirements.

Resolve ordinary details from evidence. Ask only for consequential missing choices. Check
current official docs or the installed library source when unsure about an API; do not install
a new dependency or build chain just because a generic example uses one.

## Phase 3: Implement and verify each slice

For new behavior or a bug fix with a stable contract, use tests-first where useful: run the
failing case, confirm the failure is relevant, implement, and rerun. For existing behavior,
characterize the contract before a risky rewrite. A reversible prose or low-impact style edit
does not need a test that merely mirrors implementation.

Use the actual runtime when it carries the risk: browser interactions and visual inspection
for UI, real CLI invocations for commands, API and data checks for integration. Include relevant
failure, loading, empty, retry, and persistence behavior. Keep fixture data isolated.

Record the command and working directory, observed result, and artifact revision. Passing a
typecheck alone does not demonstrate user behavior. Run the required repository gates and
broaden checks only for affected dependencies or concrete unresolved risk.

## Phase 4: Report completion accurately

In direct plan mode, mark a task complete only after its acceptance is evidenced. Append a
concise evidence note and update Status to in-progress or done as appropriate. If a plan
requires independent acceptance, route the output through /ed-verify before checking it off.

In delegated mode, return: task/attempt, assigned/used model and effort level, changed paths,
revision/diff identity, checks and results, unresolved assumptions, and the expected downstream
artifact. A successful worker report is not an ACCEPT verdict. Leave acceptance to the coordinator's
independent verifier.

Keep changes within the owned scope. If unrelated work overlaps a required file, inspect and
preserve it; stop only where ownership or intent cannot be resolved. Do not stage a shared
index while another worker owns it.

## When blocked

Use the failure to refine a falsifiable hypothesis. Reduce the reproduction and use
/ed-diagnose for a difficult cause. Honor the task's correction budget; otherwise stop after
three unsuccessful implementation attempts without progress and report the evidence. Missing
access or a contradictory requirement calls for a specific prerequisite, not repeated retries.
Do not weaken tests or acceptance to make a check pass.

## Anti-patterns

- Broadening a slice with opportunistic refactors or unrelated cleanup.
- Treating an unrun command or an unavailable service as passing evidence.
- Asking to continue work the user already requests, or ignoring their new steering.
- Completing a coordinator's plan task on the worker's own authority.

## Done when

- The requested slice works at the inspected revision and required checks have real results.
- Source follows the actual repository's conventions and scope.
- Direct work has a clear outcome; delegated work has a reviewable artifact (including model/effort record) and known gaps.

Continue to /ed-review when required by the task, or return to the coordinator for /ed-verify.
