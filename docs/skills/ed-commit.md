# Commit

A commit is the unit of history someone will `git blame`, revert, or cherry-pick a year from now. Make each one **one idea, cleanly labelled, with the reasoning that the diff can't show**. The discipline below produces commits that read like a changelog and undo like a scalpel.

---

## Phase 1: Separate the changes

One logical change per commit. A commit that does two things can't be reverted or cherry-picked without dragging the other along.

- Look at the whole working tree first (`git status`, `git diff`) before staging anything.
- Use `git add -p` to stage hunks selectively, so an unrelated fix you made along the way lands in its own commit.
- If the tree is a tangle of several changes, plan the commits first, then stage for each in turn.

---

## Phase 2: Pick the type and scope

Lead with a **conventional** type — it's a promise about the nature of the change:

`feat` · `fix` · `refactor` · `perf` · `test` · `docs` · `build` · `ci` · `chore`

- Add a scope in parentheses when it sharpens the intent: `fix(parser): …`, `feat(cli): …`.
- `refactor` means behaviour is unchanged; if behaviour changed, it's a `feat` or `fix`, not a refactor.

---

## Phase 3: Write the subject

- **Imperative** mood — "add", not "added" or "adds"; it completes "this commit will…".
- Keep it under ~72 characters, lowercase after the colon, no trailing period.
- Name the effect, not the file: `fix: reject a negative amount`, not `fix: update validation.ts`.

---

## Phase 4: Write the body — the why

The diff already shows *what* changed. The body exists for **the why** the diff can't carry: the constraint that forced it, the alternative you rejected, the subtlety a future reader will trip on.

- Blank line after the subject, wrap the body near 72 columns.
- Skip the body only when the subject is genuinely self-explanatory (a typo fix, a version bump).
- Link the issue/PR when there is one; state the trade-off when there was one.

---

## Phase 5: Breaking changes and footers

- Mark a breaking change with a `!` after the type (`feat!:`) or a `BREAKING CHANGE:` footer explaining the migration.
- No `Co-Authored-By` trailers.
- Never commit a red gate — if lint/typecheck/tests fail, fix them first; a commit is a claim that this state is coherent.

---

## Anti-patterns

- ❌ "wip", "fixes", "update", "misc" — a subject that tells the future nothing
- ❌ Bundling unrelated changes so the commit can't be reverted or cherry-picked
- ❌ Restating what the diff already shows instead of the why behind it
- ❌ Committing code that fails the gate, so the history has broken points
- ❌ `Co-Authored-By` trailers (house rule)

---

## Done when

- Each commit is one logical change, conventionally typed, with an imperative subject
- The body explains the why wherever it isn't self-evident
- Breaking changes are marked; the gate was green at every commit

Then: `/ed-ship` to push and open the PR, or `/ed-pr-fix` if you're answering review comments.
