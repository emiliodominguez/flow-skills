# Simplify

Subtract only when it improves understanding without changing required behavior. Line-count
reduction is a possible outcome, not the acceptance criterion.

## Process

1. Bound the requested cleanup and establish relevant checks. Inspect current staged/unstaged
   work and preserve unrelated changes. Find the concrete complexity: dead paths, unnecessary
   indirection, duplicate responsibility, stale comments, or generated slop.
2. Propose reduction passes by semantic risk. For a large scope, read-only reviewers can inspect
   disjoint areas when authorized; keep one writer per file. Avoid an arbitrary agent or file
   count threshold that blocks straightforward authorized work.
3. Perform a caller-check before deleting symbols: imports, dynamic lookup, registries,
   reflection, routes, configuration, templates, tests, generated sources and package exports.
   Repository search cannot see external consumers of a published API.
4. Mark a deletion **CONFIRMED-DEAD** only when supported by usage and runtime evidence.
   Keep uncertain exports or explicitly negotiate compatibility changes. Unused imported
   bindings can still evaluate a module for registration or polyfills; preserve a side-effect
   import where needed. Preserve license, compiler and tool-directive comments.
5. Inspect single-use abstractions rather than automatically inlining them. Components, Hooks,
   closures and effects carry identity, state lifetime and evaluation-order semantics even
   with one caller. A short abstraction can still express a useful contract.
6. Remove defensive guards only when actual input provenance proves them redundant. TypeScript
   annotations/assertions do not validate network, JSON, storage, DOM or JavaScript consumers.
   Do not discard a runtime invariant because the static type says it cannot fail.
7. Make small cuts, run relevant behavior and repository checks, and inspect the combined diff.
   Stop when the stated complexity is resolved; do not keep searching for more lines to delete.

## Anti-patterns

- Treating net-negative lines as a quality gate or every single-use component as waste.
- Removing imports, comments or guards using regex/type evidence alone.
- Deleting a public export because internal grep finds no caller.
- Quietly changing error behavior or component state lifetime during cleanup.

## Done when

- The targeted code is easier to understand, with semantics and compatibility preserved.
- Deletions have evidence and uncertain consumers remain explicit.
- Required checks run on the resulting artifact, not only on an earlier baseline.

Use /ed-review for the diff or /ed-refactor for a separate ownership/structure problem.
