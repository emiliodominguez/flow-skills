# Ship

Complete the delivery action the user requests. A push, draft PR, ready transition, merge,
deployment, and publication are distinct outcomes; one does not authorize all the others.

## Phase 1: Establish the terminal action

Read current authorization, repository delivery rules, branch/remotes, status, and existing PR
metadata. Resolve base/head and target remote from evidence. Reuse an existing appropriate PR.
Do not prompt again for an already authorized action, and do not treat a skill handoff as
permission for an unrequested merge, deployment, reviewer request, or message.

## Phase 2: Verify the artifact

Inspect committed, staged, unstaged and relevant untracked changes separately. Preserve user
work and review the actual artifact that will be committed. Run the repository's pre-launch
checklist: required formatting, lint, types, tests, build, generated docs, and relevant runtime
checks. Use /ed-review where the task or repository requires review.

Record the verified revision/diff. If hooks or CI fixes change behavior later, repeat the
affected checks and review before declaring the new artifact ready. Missing access and unrun
checks remain explicit; a previous green revision does not verify the current one.

## Phase 3: Commit and push when requested

Use atomic commits and the conventional-commit policy from /ed-commit. Never bypass a hook.
After a failed plain commit, retry a new commit after fixing the problem; do not amend the
unrelated previous commit. Preserve an intentionally requested amend only after checking HEAD.

Push to the identified remote/branch with ordinary fast-forward behavior. For conflicts or
rewritten history use /ed-git-fix; do not force-push as a routine retry. Verify the remote head.
Do not let a CLI silently choose a fork or push target when the intended destination is unknown.

## Phase 4: Create or update the requested PR

For a requested draft, stop at draft. For a requested ready PR, use the repository's actual
workflow; draft-first is useful when checks must run before readiness, not a universal gate.

Write a concise body: the problem, change, resulting behavior, validation, and meaningful
limitations or rollback considerations. Use a structured tool field or a body file with real
newlines. Do not add reviewer notifications or comments unless requested.

Inspect workflows and checks on the current head. Distinguish passed, failed, pending, skipped,
and absent checks. Some workflows trigger only on `ready_for_review`; others are disabled.
Do not deadlock on a check that cannot start in draft, or label absent CI as passing. Observe
bounded waits and report outstanding required checks. Promotion or merge still follows the
requested terminal action and repository requirements.

## Phase 5: Confirm the result

Verify the remote SHA, PR URL, draft/ready/merged state, and check summary that apply. If merge,
deployment, or publication is explicitly requested, complete its concrete preparation and
required gates before that action. Otherwise finish at the requested stage with a usable link.

## Anti-patterns

- Turning "push this" into a ready PR, reviewer ping, merge, and deployment.
- Claiming review passed after adding unreviewed behavioral fixes.
- Treating missing CI as green or endlessly waiting for a disabled workflow.
- Editing or discarding unrelated staged work to make delivery convenient.

## Done when

- The authorized delivery stage is reached and confirmed against remote state.
- Verification belongs to the delivered revision and any remaining limits are visible.
- The user has the commit or PR reference needed to inspect the result.

Use /ed-pr-fix for subsequent review feedback or /ed-git-fix for a demonstrated Git problem.
