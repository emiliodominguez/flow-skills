# Fix PR feedback

Map every actionable discussion to a disposition and evidence. Do not announce or resolve a
fix that reviewers cannot inspect on the published revision.

## Process

1. Resolve the exact repository/PR, base/head, current commit SHA and local work state. Read the
   description, reviews, threads and checks, including pagination. Track resolved, outdated and
   already-addressed feedback so a rerun does not send duplicate replies.
2. Normalize conversations: keep the root review comment ID separate from the GraphQL thread
   ID. GitHub review replies target the root comment, not another reply. Issue comments and
   review threads are different channels. Use connected tools or `gh api` only when available
   and authorized, with current API shapes.
3. Group by intent and classify each actionable item: fix, already fixed, needs evidence,
   disagreement, or out of scope. Resolve apparent reviewer conflicts against contracts and
   source; ask only when a consequential decision remains genuinely ambiguous.
4. Make logical changes, preserving unrelated staging/work. Run relevant tests and repository
   gates; review substantive behavior changes. Preserve unsquashed fix commits when repository
   review practice needs traceability, rather than rewriting public history by default.
5. Prepare a response map: thread/root ID, disposition, exact change, commit/file evidence and
   validation. A local-only request ends with local fixes and concrete reply drafts.
6. When publishing is authorized, push and confirm the remote head contains the fix. Only then,
   if replies/resolution are also authorized, post concise evidence-backed responses and resolve
   fully addressed threads. Keep disagreement or missing evidence open. Check whether the action
   already succeeded before retrying after an uncertain response.
7. Re-fetch the PR state and confirm what is actually published, answered, resolved or still
   pending. Assess checks on the latest head rather than trusting an earlier green commit.

## Anti-patterns

- Replying "fixed" with an unpublished commit SHA or resolving before a failed push.
- Treating every historical thread as new work or replying to a reply ID.
- Accepting every suggestion without checking the behavior contract.
- Sending comments or reviewer notifications merely because code changes are authorized.

## Done when

- Every thread with current actionable feedback has a clear disposition.
- Requested fixes are verified and their publication status is accurate.
- Authorized replies/resolutions refer to visible evidence and remaining disagreements stay open.

Use /ed-review for affected behavior or /ed-ship for the remaining authorized delivery action.
